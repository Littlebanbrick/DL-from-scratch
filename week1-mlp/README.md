## Q1 · 时间花在哪

`torch.profiler` 录 8 步（2 步热身不计），看 `Self CPU %` 排序。

| hidden | `mm`+`addmm` 自身占比 |
|---|---|
| 32 | 24.5% |
| 128 | 42.9% |
| 512 | 59.5% |

h=512 时矩阵乘是大头，不是框架开销。但 h=32 时降到 24.5%——**「哪段 compute-bound」取决于模型多大**，没有固定答案。

## Q2 · batch_size 的拐点

| bs | 步数/epoch | 单步 min | 外推 epoch | 实测 epoch |
|---|---|---|---|---|
| 32 | 1875 | 0.342 ms | 0.64 s | 4.21 s |
| 128 | 469 | 0.881 ms | 0.41 s | 3.67 s |
| 512 | 118 | 2.765 ms | 0.33 s | 3.36 s |
| 2048 | 30 | 10.648 ms | 0.32 s | 3.41 s |

epoch 时间只掉了 19%，纯算力却掉 50%。差的那 3 秒是数据管线，与 batch_size 无关。


顺带：固定 `lr=1e-3` 时准确率随 bs 下降是真的，但原因是更新次数（bs=32 是 bs=2048 的 65 倍），不是大 batch 本身学得差。

## Q3 · 数据是不是瓶颈

| 操作 | 耗时 |
|---|---|
| 6000 样本，无 transform | 24.3 ms |
| 6000 样本，有 transform | 278.9 ms → 外推整轮 2.79 s |
| DataLoader 整轮（bs=32） | 2.23 s |
| DataLoader 整轮（bs=2048） | 2.26 s |

无 transform 时几乎免费，加了 `ToImage`+`ToDtype` 就慢 11 倍。瓶颈是逐样本的 Python 调用，6 万个样本吃 2.2 秒。

模型整轮只要 0.32–0.64 秒。数据是模型的 4–7 倍，并且和 batch_size 无关。


## Q4 · 模型变大的缩放

| hidden | 单步 min | MAC/样本 | 相对 h=128 | 有效吞吐 |
|---|---|---|---|---|
| 32 | 0.156 ms | 2.6 万 | 0.58× | 21.7 GMAC/s |
| 128 | 0.267 ms | 11.8 万 | 1.00× | 56.6 GMAC/s |
| 512 | 0.888 ms | 66.9 万 | 3.33× | 96.4 GMAC/s |
| 1024 | 2.398 ms | 186 万 | 8.98× | 99.4 GMAC/s |

MAC = `784h + h² + 10h`；吞吐按前向 MAC 算（含反向，故为相对指标）。

h 从 128 到 512（4 倍），时间只涨 3.33 倍；从 512 到 1024（2 倍），涨 2.70 倍。吞吐在 512 后饱和在 ~100 GMAC/s——**再往上加宽度只是按比例变慢，效率不再提升。**

小模型的时间大半花在固定开销上。
