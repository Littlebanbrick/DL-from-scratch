## 引擎设计

`Value` 存五个字段：`data`（数值）、`grad`（梯度）、`children`（产生它的两个输入）、`op`（算子名）、`_backward`（这个节点自己的局部导数）。

**与 micrograd 原版的一处差异**：原版存 `_prev`（指向输入）并把 `_backward` 定义成 `Value` 的方法；本实现把 `_backward` 作为闭包挂在实例上，闭包直接捕获 `self`、`other`、`out`。

两种写法等价，但闭包方案有一个后果，见下面「坑 2」。

**拓扑排序**：从输出出发 DFS 所有 `children`，后序追加，最后反向遍历调用 `_backward`。必须做，因为图是 DAG 不是树——同一节点可能被多条路径消费，不做排序会在梯度还没传全时就被读取。

## 训练设定

- 损失：hinge `max(0, 1 - y·pred)`，只用一个 `.relu()` 就拼出来，不用给引擎加新算子
- 标签 `+1/-1`，输出层线性，`pred` 可解释为到超平面的距离
- 全批量（100 样本一步），不做 minibatch——这一周要看的是引擎本身
- 数据先归一化到 `[-1,1]`，否则 relu 之后数值尺度失控

结果：200 步收敛到 acc 0.90，见 `moons.png`。

## 踩到并修掉的三个问题

### 坑 1 · `backward` 被实例属性遮蔽

`__init__` 里写了 `self.backward = lambda: None`。Python 属性查找实例优先于类方法，所以真正做拓扑遍历的类方法 `backward()` **永远调不到**——`loss.backward()` 实际执行的是当前算子那个只更新局部梯度的闭包。

症状：`a.grad`、`b.grad` 全是 `0.0`。

修法：实例属性改名 `_backward`，类方法保留 `backward`（和 PyTorch 约定一致）。

### 坑 2 · 引用环让 GC 成为主要开销

`out._backward` 闭包捕获了 `out` 自己 → **引用环**。引用计数释放不掉，只能等 Python 的循环垃圾回收器扫描。

实测（`gc` 开，同一份代码跑三次的 median）：

```
11.8 / 98.2 / 120.1 ms
```

关掉 GC：

```
8.06 / 7.99 / 7.97 ms
```

**不仅稳定，还快了 30%。** 训练循环里已经 `gc.disable()`。

这也意味着：PyTorch 张量没有引用环、出作用域立即释放，**不关 GC 的引擎 vs torch 对比本身就不公平**——比值里混进了 GC 开销，不是引擎设计的差异。

### 坑 3 · `tanh` 用 `exp(2x)` 会溢出

`math.exp(2x)` 在 `x>350` 抛 `OverflowError`。这是已知局限，不是待修 bug——gradcheck 的测试点限制在 `|x|<5`。

顺带一个设计点：`tanh` 的导数 `1 - tanh²` 只需要前向结果，所以必须**复用前向输出**（`res`）而不是重算。这就是「计算图保存中间结果」的动机。

## 正确性门禁（M6）

两道独立判据：

**第一道 · 跟 PyTorch 对拍**（Karpathy 原版两个测试）

复杂的嵌套表达式，两边梯度和逐位一致（`assert ==`，不是近似）。

**第二道 · 有限差分 gradcheck**

```
数值梯度 = (f(x+ε) - f(x-ε)) / (2ε)      中心差分
解析梯度 = backward() 的结果
相对误差 <= 1e-6 才算过
```

关键实现细节：**每次都新建一张图**。复用同一批 `Value` 会让梯度累加，测出来的东西是假的。

覆盖 8 个单算子 + 5 个组合：

| 类型 | 用例 |
|---|---|
| 单算子 | add / sub / mul / div / pow / pow 负指数 / exp / tanh / relu（正负两侧） |
| 同节点复用 | `a*a`，且 `a*a + a` 的梯度必须等于 7.0 |
| 多路径累加 | `a*b + a`，`d/da = b + 1` |
| 混合链式 | `(a+b).tanh()*a` |
| 深层嵌套 | 四层非线性复合 |
| 梯度累加行为 | 两次 `backward()` 梯度翻倍；清零后重算结果一致 |

`python test.py` → **16/16 passed**。

### 验证测试本身有没有牙齿

全过的测试可能什么都没测。做了两次变异测试，故意把引擎改坏：

| 变异 | 被哪些测试抓到 |
|---|---|
| `tanh` 导数 `(1-res²)` → `(1-res)` | `test_grad_tanh`、`test_grad_chain`（14/16） |
| `__add__` 的 `grad +=` → `grad =` | `test_more_ops`、`test_sanity_check`、`test_grad_chain`、`test_grad_deep_chain`（12/16） |

两次都抓到了，说明门禁是活的。

已知盲区：变异 2 里 `test_grad_shared_node` 和 `test_grad_multipath` 没触发——拓扑顺序让覆盖发生在累加之前，那时 `a.grad` 本来就是 0，差别被掩盖。要更严需要补「同一输入被两个不同的加法消费」的用例。

## 跟 PyTorch 对打（M7）

同一个 MLP（2→8→8→1，两边都是 105 个参数），同一份数据，`float64` 对齐，`cpu_threads 8`，GC 关闭，`bench()` warmup=3~5 / N=20 取最小值。

| 阶段 | 本引擎 | PyTorch | 倍数 |
|---|---|---|---|
| 纯前向（含建图） | 7.924 ms | 0.0211 ms | **376×** |
| 前向 + 反向 | 15.077 ms | 0.0834 ms | **181×** |
| 完整一步（含更新） | 15.028 ms | 0.1075 ms | **140×** |

`train.py` 里 200 步的独立测量：median 15.35 ms / step，与 `compete.py` 的 15.03 一致。

### 拆开看

```
本引擎：前向 7.9 → 反向 +7.2 ms     反向 ≈ 前向
torch：前向 0.021 → 反向 +0.062 ms  反向 ≈ 前向 ×3

参数更新：15.077 → 15.028，几乎免费（105 次 p.data -=）
```

反向/前向的比例两边一致，说明 `_backward` 的实现没有多余开销，慢在数量级上，不在实现质量上。

### 为什么慢 100–400 倍

105 个参数 × 100 个样本，一次完整一步要创建上万个 `Value` 对象，每个都触发若干次 Python 函数调用和属性查找。PyTorch 一次 C++ 调用就完成 100×8 的矩阵乘，内部是 BLAS。

**比值随「做的事越多」而下降**（376 → 181 → 140），因为 torch 的固定调用开销被摊薄，而本引擎是线性增长。

这条规律和 Week 1 的 Q4 是同一件事：小规模下固定开销压倒一切。

## 未做 / 已知局限

1. **批处理不对称**：本引擎逐样本循环，torch 一次吃 `[100,2]`。这不是不公平——**它就是差异的来源**，但结论应该说成「纯 Python 标量引擎 vs 张量框架」，而不是两个等价实现。
2. **初始化不同**：本引擎 `random.uniform(-1,1)`，torch 用 `kaiming`。所以训练轨迹不同。这是计时对比，数值一致性由 `test.py` 负责。
3. **`train.py` 的决策边界格子慢**：1600 次前向，纯 Python，耗时打在图上标题里。
4. **没测 batch 变大时比值怎么变**：预期比值缩小，可以直接验证上面的缩放分析，但没做。
5. **`draw.ipynb` 的模块缓存坑**：改了 `value.py` 必须重启内核，否则 `from value import Value` 拿的是旧的缓存类。`.py` 脚本没有这个问题。
